# GlobalUserSettingsManager

Dataverse solution that defines default values for the `usersettings` table, rolls them out to existing users, applies them to new users, and optionally locks settings (user changes are reverted). Defaults can be grouped by Team and Business Unit, with priorities.

## Architecture in one paragraph

Config lives in `jhrb_settingsprofile`: Global, Group and User rows, each with a value column and a `_mode` column per managed setting. `jhrb_profilescope` holds the group rules (Team / BU, OR). Effective value per user and setting comes from the layer chain User > Group (by priority) > Global, where the first non-Inherit layer wins value and lock. Locks are enforced by a sync PreOperation step on `usersettings` Update (silent revert, own edits only); admin edits of others are captured into the user's override row. Changes roll out through `jhrb_rolloutjob` rows, processed in chunks by an async plugin. Jobs come from profile and scope changes, team membership, new users, the `jhrb_ApplyDefaults` / `jhrb_ReconcileSettings` Custom APIs, and a daily heartbeat (recurring bulk delete of `jhrb_heartbeat`). `jhrb_userstate` keeps each user's layer fingerprint, so the reconcile re-applies defaults only to users whose layers changed. `jhrb_settingslog` (elastic, 90-day TTL) records every revert and rollout write.

## Hard rules

- **No Power Automate.** All data changes via C# plugins and Custom APIs.
- `usersettings` has no Create message and not every attribute is writable. Generate the settings column list from metadata (`IsValidForUpdate`), never hand-write it.
- `SettingsRegistry` (generated from `schema/managed-settings.csv`) maps usersettings attribute -> value column `jhrb_<attr>` -> mode column `jhrb_<attr>_mode` (global choice `jhrb_settingmode`: Inherit 632490000 / Default 632490001 / Locked 632490002). Adding a setting = one CSV line, then Build-Schema + Deploy-Schema. No other code lists settings.
- Lock enforcement is **silent revert only** (Block tested: Personal Options shows no error). It only applies to a user's own edits (`InitiatingUserId == target`).
- Global row `jhrb_pilotteam` limits everything to that team's members; Global inactive = feature off. In the shared dev env the pilot team must stay set.
- Plugins are stateless: no static caches, per-execution caching only. Idempotent everywhere. Rollout writes use `UpdateRequest` with `Parameters["tag"] = "jhrb_rollout"` and set `SharedVariables["jhrb_rollout"]`, so the lock plugin neither reverts nor captures them. Any new code that writes `usersettings` must do the same.
- Plugins on `systemuser` Create, Associate/Disassociate and `systemuser` Update must never throw: they only queue jobs.
- Never write `usersettings` for many users inline in a plugin step. Create a `jhrb_rolloutjob`; rollout stays under the 2-minute plugin limit by chunking with a persisted cursor.
- Only update attributes whose value differs from the effective value.
- No secrets, no external calls in plugins.
- Plugin steps are registered through the solution (`pac plugin` / solution components), not by hand in the Plugin Registration Tool.
- Check current official Dataverse requirements (plugin target framework, signing, limits) before pinning versions. Default: classic plugin assembly on .NET Framework 4.6.2 unless NuGet dependencies force a plugin package.

## Commands

```powershell
pac auth list                         # confirm the target environment first
pwsh scripts/Build-Schema.ps1         # after editing managed-settings.csv
dotnet build src/DefaultUserSettings.Plugins -c Release
dotnet test src/DefaultUserSettings.Plugins.Tests
pwsh scripts/Deploy-Schema.ps1; pwsh scripts/Register-Plugins.ps1; pwsh scripts/Deploy-Security.ps1; pwsh scripts/Deploy-App.ps1
pwsh scripts/Seed-GlobalProfile.ps1 -PilotMembers <userid>; pwsh scripts/Setup-Heartbeat.ps1
pwsh scripts/Test-Integration.ps1     # Phase 1, own user only
pwsh scripts/Test-Rollout.ps1         # Phases 2-4, own user only (must be the only pilot member)
pwsh scripts/Test-RoleAccess.ps1 -AsUser <userid>   # pages' calls as a non-admin (impersonation); give that user Basic User + Admin first
pwsh scripts/Export-Solution.ps1      # unmanaged + managed zips, unpacked source in solution/
cd src/GenPages; npm ci; npm run check; cd ../..; pwsh scripts/Deploy-GenPages.ps1   # generative pages (then runs Deploy-App.ps1)
cd src/CodeApp; npm ci; npm run build; npx --no-install pa app push -s <solution id>   # code app (needs `pa app init` once)
```

Never edit `SettingsRegistry.g.cs` or `schema/settings.json` by hand.

Installed: PAC CLI 2.14.1 (has `pac model genpage`), .NET SDK 9 and 10. Plugin assembly still targets net462 (needs the .NET Framework targeting pack / reference assemblies).
